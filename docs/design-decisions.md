# Design decisions

## Start with an artifact a small project already has

The input is a pytest JUnit XML file generated by the user. A failing unit test is a concrete, repeatable event, and a local Git repository usually contains enough context to investigate it. The tool does not require access to a production service, a private monitoring platform, or an organization's incident history.

The first useful output is a reviewable bundle: failure text, relevant source lines, a selected diff, related rules, and next checks. Collecting those pieces is a tractable scope; proving the cause of an arbitrary failure is not.

## Let the user choose the comparison

`HEAD`, `HEAD~1`, and a release tag answer different questions. A tool cannot infer which version last passed a test simply by reading a working tree. Git context is optional and requires an explicit baseline. The report should retain that choice so that a reader can interpret the diff.

## Keep retrieval optional

A new failure does not need a matching historical case. Failure text and the current code are primary evidence. Local Markdown retrieval adds project-specific constraints: inclusive boundaries, rounding rules, expected exceptions, or environment requirements. It is useful only when such rules exist and are relevant.

For a small directory of notes, an in-memory lexical index is sufficient. A separate vector database and a mandatory embedding download would add setup cost before the basic workflow becomes useful. The main analysis workflow uses BM25 for these notes.

## Separate facts, hypotheses, and commands

“An assertion expected 90 and received 100” is an observation from the test result. “The boundary comparison may exclude the exact threshold” is a hypothesis to verify. “Run this one test” is a proposed check. Keeping these distinct helps users decide what is established and what still needs work.

Evidence references make a claim inspectable; they do not make it true. A valid quote can be used to support an invalid inference. Optional model output is an explanation layer and must not override the collected observations or hide a failure to produce a valid explanation.

## Read a project without executing it

The analysis command reads XML, selected source files, notes, and Git changes. It does not import the target project, execute a suggested command, or apply a patch. The separate demo generator runs only the small fixture that it creates, so its test execution is explicit and reproducible.

A local HTTP form is a convenience around the same operation. Because it accepts local filesystem paths and has no user accounts, it belongs on loopback rather than a public server.

## Keep scope visible

JUnit XML varies by producer. Tracebacks can omit source paths; native extensions and parametrized tests can be hard to map back to a file. A source file may have changed since the XML was produced. These cases should leave missing context visible, not become confident root-cause claims.

A constructed cart example is a pipeline demonstration, not evidence of use by a company or a broad accuracy estimate. More convincing validation comes from retaining failures, adding independent examples, and checking report evidence against the actual files.
